01

项目定位

这不是量化交易软件，不是自动交易机器人，也不是交易终端。它是一个个人交易工作台（Personal Trading Workspace）——你的交易行为、市场数据、AI 判断长期沉淀在一个地方，随时间越用越懂你。

核心主张

记录 → 数据积累 → 分析 → 复盘 → AI 辅助决策。AI 不负责替你交易，只负责基于你的历史和当前市场给出分析与提示，最终决策权始终在你手里。

02

第一版只解决「每天真正会做的事情」，克制比完整更重要。

03

核心设计原则

3.1数据库只保存事实

数据库只保存真实发生过的、不可再生成的数据：开仓 / 平仓 / 数量 / 时间 / 价格 / K 线 / 新闻。不保存 MA / RSI / MACD、盈亏率、AI 分析结论这类可以被重新计算出来的派生数据——它们全部实时计算，保证任何时候「换一种算法」都不需要动数据库。

3.2用户只输入系统不知道的数据

用户只负责输入系统无法推断的信息：开仓价格、平仓价格、数量、备注。当前价格、当前持仓、平均成本、持仓时间、盈亏、技术指标、相关新闻——这些系统必须自己算出来，绝不让用户手填。

3.3历史数据是永久资产

行情数据下载一次，长期保存，此后图表、指标、AI、未来的回测与策略研究全部复用同一份数据仓库，不重复拉取、不重复计算。

3.4极简记录：一次交易 20–30 秒

记录一次交易的表单字段被压缩到最少：市场、品种、操作、价格、数量、可选备注。这是贯穿整个交互设计的硬约束，任何新功能如果拉长了这个流程，都要重新评估必要性。

06

数据模型设计

系统划分为三个物理隔离的数据库，边界清晰，互不越权读写。

6.1Trading Database — 你的事实

trading.db
Workspace     -- 工作区：Trading / Research / Learning / Simulation，彼此隔离
Portfolio     -- 归属某个 Workspace，可理解为一个资金账户
Position      -- 当前持仓快照，由 Transaction 聚合得出
Transaction   -- 一次真实操作：开仓 / 加仓 / 减仓 / 平仓
Watchlist     -- 关注的品种 + 触发条件
Report        -- 已生成的日/周/月报（内容存正文快照）
Notification  -- 已发出的提醒记录
Note          -- 用户手动备注 / 复盘笔记

6.2Market Data Warehouse — 市场的事实

market.db
Crypto / Stock / Future   -- 按市场分表，统一 OHLCV 结构

OHLCV {
  symbol, interval, open_time,
  open, high, low, close, volume
}

-- 后续扩展，不影响现有结构：
Funding        资金费率（合约）
OpenInterest   持仓量
News           新闻 / 公告
Earnings       财报
MacroEvent     宏观事件

6.3Vector Database — AI 的记忆

chroma / collections
daily_report      AI 生成的日报正文，供未来复盘检索
weekly_report
monthly_report
news_summary      新闻摘要 + 与持仓的关联判断
strategy_note     策略说明 / AI 对某次信号的推理过程
chat_history      AI Chat 对话记录，作为长期上下文
已裁决 · 数据库物理拆分方式

采用「业务数据库一个 + 市场数据库一个」，而不是每个市场单独一个 SQLite 文件。市场用 market 字段区分（crypto / stock / future），共享同一套 OHLCV 表结构与业务逻辑，避免后续新增市场时要复制一整套 schema。

07

持仓生命周期：Position + Transaction

整个系统围绕 Position 而不是围绕 Order 设计——这是决定后续所有交易记录体验的核心建模选择。

Transaction #1 开仓
→
Transaction #2 加仓
→
Transaction #3 减仓
→
Transaction #4 平仓
→
Position 归档

Position 表示「当前持仓」这个状态本身；Transaction 表示「一次操作」这个事件。Position 的均价、数量、盈亏全部由其下的 Transaction 序列实时聚合计算得出，从不单独存储。

这个模型天然支持分批建仓、分批止盈、网格、马丁格尔等复杂操作模式，不需要为这些场景单独扩展数据库结构——它们本质上都只是「同一个 Position 下更多的 Transaction」。

7.1交易记录表单（用户实际填写）

字段示例是否必填
市场Crypto必填
品种BTCUSDT必填
操作开仓必填
价格108200必填
数量0.2 BTC必填
备注—可空

其余一切——当前价格、持仓均价、持仓时长、浮动盈亏、相关技术指标、相关新闻——均由系统在读取时实时计算，用户不填写、数据库不存储。

08

行情数据更新策略

已裁决：定时更新为主，手动刷新为辅。这一层本期不是重点，先做到「够用、不阻塞其它模块」，具体调度精度留待接入真实数据源时再细化。

定时更新（主）

APScheduler 按周期任务拉取，不同 K 线周期采用不同更新频率：

  • 1m / 5m — 高频，仅对当前有持仓 / Watch 的品种
  • 1h / 4h — 中频，覆盖 Watchlist 全部品种
  • 1d — 低频，每日收盘后统一补齐

手动刷新（辅）

用户在图表页 / 持仓页可随时点击「立即刷新」，强制拉取该品种最新数据，用于定时任务尚未触发时的即时查看需求。

实现建议：更新任务只做「增量补齐」——记录每个 (symbol, interval) 的最新已存时间戳，每次只拉取缺口部分，避免重复下载已永久保存的历史数据。

09

技术指标引擎

统一计算入口，输入 OHLCV 序列，输出指标值。数据库不保存任何指标结果，全部实时计算，保证换算法、改参数不需要数据迁移。

MAEMAMACDRSI BOLLATRKDJADXCCI … 后续增加
10

策略引擎

已裁决：插件化目录，用户可通过配置启用 / 禁用策略。每个策略是一个独立文件，实现统一接口，系统启动时自动发现并注册，新增策略不需要改动核心代码。

所有策略统一输出同一种结构，供 Watch 模块和 AI 触发层消费：

strategy.output.schema
{
  "signal": "BUY",           // BUY / SELL / HOLD
  "score": 82,               // 0-100 强度
  "confidence": 0.74,       // 0-1 置信度
  "reason": "MA突破"       // 人类可读的触发原因
}
与其它模块的关系

策略产生的 Signal 是 AI 触发抽象层里「事件触发」的天然输入源之一——策略发现机会，触发层决定是否值得叫醒 AI 做进一步分析，两者职责分离。

11

AI 触发抽象层

这是本版设计相对 v0.1 新增的核心部分。原方案里「早报 / 盯盘发现机会 / 周报月报 / 用户主动提问」是四个各自独立实现的场景，容易导致 AI 调用逻辑散落在各处、重复消耗 token。这里把它们统一抽象成一层。

11.1设计目标

把「什么时候触发 AI」「AI 分析什么」「结果发到哪里」三件事解耦，新增一个触发场景（例如未来的「资金费率异常提醒」）只需要注册一条 Trigger 配置，不改动 AI 核心调用逻辑。

11.2三种触发类型

类型说明对应场景
Scheduled
定时触发		cron 表达式驱动每天 08:00 早报、每周日周报、每月 1 日月报
Event
事件触发		由业务事件 + 过滤条件驱动Watch 命中价格阈值、策略产生高置信度 Signal、新增 / 平掉一笔持仓
On-Demand
主动触发		用户在 AI Chat 里直接提问，或点击「立即分析」用户随时追问持仓、行情、某条新闻

11.4Trigger 注册表结构

ai_trigger.schema
{
  "trigger_id": "daily_briefing",
  "type": "scheduled",             // scheduled | event | on_demand
  "condition": "0 8 * * *",         // cron，或事件类型+过滤条件
  "context_scope": {
    "positions": "all_open",
    "lookback_days": 7,
    "include_news": true
  },
  "prompt_template_id": "daily_briefing_v1",
  "output_target": "notification + report",
  "cooldown_minutes": 1440       // 防止重复触发
}

11.5去重与限流

Context Assembler 在组装前先检查该 Trigger 的 cooldown 是否已过期、以及触发时的关键上下文（如持仓状态）相较上次是否发生实质变化，两者都满足才真正调用 AI。这是解决 v0.1 遗留问题「如何避免重复分析和无意义消耗」的具体机制。

11.6输出结构化

AI 的返回统一由 Output Parser 解析为结构化结果（结论 / 风险等级 / 置信度 / 建议行动），而不是一段自由文本——这样同一份结果既能推送成通知，又能写入 Report，还能作为未来 AI 分析的历史上下文，一份产出三处复用。

13

新闻与舆情

系统自动获取新闻、公告、宏观数据、ETF 资金流、行业资讯，存入 Market Data Warehouse。AI 负责在此基础上做二次加工：

  • 摘要总结
  • 自动分类
  • 与当前持仓关联判断（这条新闻是否影响我手上的品种）
  • 影响程度判断，作为 Event Trigger 的候选输入
14

Watch 提醒

持续监控价格、指标、策略 Signal、新闻四类信号源，任一条件达到设定阈值即产生 Notification，同时可作为 AI Event Trigger 的输入源，实现「先提醒、AI 再补一句为什么」的组合体验。

15

Report 报表

日报 / 周报 / 月报由 Scheduled Trigger 驱动自动生成，内容包含收益、回撤、持仓变化、市场总结、AI 建议，正文快照存入 Trading DB 的 Report 表，同时写入 Vector DB 供未来检索复盘。
